# RPP Repo Docs

An app repository keeps its documentation in `docs/`. The central portal
`RocketPadPlatforms/docs` (Docusaurus 3.10, https://docs.rpp.gmbh) fetches `docs/` at every
**released tag** and publishes it as one product:

```
https://docs.rpp.gmbh/<app-id>/            latest release
https://docs.rpp.gmbh/<app-id>/<version>/  older releases (banner, noindex)
```

Released tags are immutable and must keep building for years, so write conservatively. Do **not**
add a Docusaurus site, `package.json` or build config to the app repository: the portal owns all
of that.

## Before you start

1. Find the app's entry in the portal (the portal is `RocketPadPlatforms/docs`, branch `main`):
   `https://raw.githubusercontent.com/RocketPadPlatforms/docs/main/docs-sources.json`.
   Match on `repo`. Note its `id` (the URL segment), `label`, `docsPath` and `sidebarFile`.
   - Entry found: use those values, and keep `docsPath` and `sidebarFile` as configured.
   - No entry: the app is not registered yet. Continue with the work, use a placeholder id for
     URLs, and finish by proposing the entry (template below). The local build check needs the
     entry, so say that it could not be run.
2. Inventory the existing documentation (README sections, an existing `docs/` or Docusaurus
   site, pages coming from `RocketPadPlatforms/platform-docs`). List every page with its current
   path or URL.

## Hard rules

The portal build fails or misbehaves otherwise.

1. Everything lives in `docs/`. Nothing in it may import, include or relatively link anything
   outside `docs/`, except the `@theme/*` and `@site/*` imports listed under "What is
   available". No symlinks (the fetch rejects them).
2. **Sidebar:** `docs/sidebars.json`, a JSON object with exactly one sidebar named `docs`, items
   are doc ids. Categories link to their index doc
   (`"link": {"type": "doc", "id": "<folder>/index"}`), never `generated-index`: its URL is
   derived from the label and breaks silently when the label changes. Omitting the file is
   allowed (an autogenerated sidebar is used), but prefer an explicit one. No
   `sidebars.js`/`.ts`: they run code during the build. See
   `references/sidebars.example.json`.
3. **Start page:** `docs/index.md` with `slug: /` in the front matter.
4. **Front matter** on every page: `title` (unique across all RPP products, so name the product
   where a title would be generic, e.g. "Install App A"), optional short `sidebar_label`, and
   `description` (1-2 plain sentences, used by search engines). One H1 per page: either none
   (then `title` is rendered) or a `# Heading` identical to `title`. See
   `references/frontmatter.md`.
5. **Links** between docs are relative file paths with extension:
   `[Install](./installation.md)`, `[Ports](../reference/configuration.md#ports)`. No absolute
   `/docs/...` or `https://docs.rpp.gmbh/...` links to pages of this product (links to other RPP
   products may use their absolute URL).
6. **Assets** live in `docs/assets/` (or beside the page) and are referenced relatively:
   `![Architecture](../assets/architecture.svg)`. Every image has alt text.
7. Files and folders starting with `_` are not pages. Reusable snippets go to
   `docs/_partials/_name.mdx` and are imported relatively.
8. **Doc ids must stay stable across releases**, so the version dropdown can map a page to the
   same page in another version. The id is `<folder>/<base>`, where `<base>` is the file name
   without extension or the front matter `id`. The front matter `id` replaces only the base and
   cannot contain a slash. So:
   - renaming a file inside its folder: keep the old base with `id: <old-name>`;
   - moving a file to another folder always changes its id. Avoid it; if unavoidable, set `slug`
     to keep the URL (the dropdown then falls back to the version's start page for that page).
9. **MDX 3** (with MDX 1 compatibility) parses `.md` and `.mdx`. Escape `{`, `}` and `<` in prose
   (`\{`, `&lt;`) or put them in code spans or fences. Close every HTML tag (`<br />`). Use
   `import`/`export` only for partials and the components below.

## What is available (nothing else)

- Admonitions `:::note`, `:::tip`, `:::info`, `:::warning`, `:::danger`, optionally with a title.
- Code fences with titles and line highlighting. Languages: Prism defaults plus `bash`/`shell`
  and `hcl`. Mermaid diagrams in ```` ```mermaid ```` fences.
- `@theme/Tabs`, `@theme/TabItem`, `@theme/Admonition`, `@theme/CodeBlock`, `@theme/Details`.
- Portal components (they change for **all** versions at once, use sparingly):
  `@site/src/components/ClusterLink`, `@site/src/components/Icons`, `@site/constants`.
- HTML comments `<!-- -->`, custom heading ids `## Ports {#ports}`, emoji shortcodes.

## Structure

Use the Diataxis split and lowercase, hyphenated file names. Do not mix tutorials, how-tos,
explanation and reference on one page; split anything longer than about 1500 words.

```
docs/
  index.md                  slug: /   what it is, who it is for, where to go next
  sidebars.json
  getting-started/          index.md, requirements.md, installation.md, quick-start.md
  concepts/                 index.md, architecture.md, ...           (explanation)
  guides/                   index.md, <one task per page>.md          (how-to)
  reference/                index.md, configuration.md, cli.md, ...   (facts, tables, defaults)
  troubleshooting.md
  _partials/                reusable snippets (not pages)
  assets/                   images and downloads
```

Details and rationale: `references/structure.md`.

## Workflow

1. Propose the target tree and a mapping table: old path or URL, new file, new doc id, new public
   URL (`https://docs.rpp.gmbh/<app-id>/<path>/`). If more than a handful of pages move, wait for
   confirmation before moving files.
2. Create or move the files, write front matter, fix every relative link and image path, write
   `docs/sidebars.json`. Do not change product facts. Collect anything unclear in a `TODO:` list
   in your answer, not inside the docs.
3. Add `.github/workflows/docs.yml` from `references/docs-workflow.yml` (no `paths:` filter: it
   becomes a required check). Fill in `app-id` and `docs-path`.
4. Verify against the portal (needs the app registered there). Requires Git and Node.js 24
   (Linux, macOS and Windows). Run pnpm through `corepack` (bundled with Node): it installs the
   exact pnpm version the portal pins, which a system-wide pnpm cannot do on every platform.
   On NixOS, first enter `nix shell nixpkgs#nodejs_24 nixpkgs#git` (it opens a new shell). If
   `corepack` is missing, run `npm install -g corepack`.

   ```bash
   git clone https://github.com/RocketPadPlatforms/docs ../rpp-docs   # once
   cd ../rpp-docs
   corepack pnpm install --frozen-lockfile
   corepack pnpm dev:local -- <app-id>=<path-to-this-repo>/docs --build   # production build, fails on broken links and MDX errors
   corepack pnpm dev:local -- <app-id>=<path-to-this-repo>/docs           # preview with hot reload, http://localhost:3000/<app-id>/
   ```

   The commands are the same in bash, zsh and PowerShell; forward slashes work in paths on
   Windows. The sidebar is read once at start; restart the preview after editing it.
5. Finish with:
   - the mapping table (old to new URL; the portal's `legacy-redirects.json` needs it),
   - the registration entry if the app is not in `docs-sources.json` yet:

     ```json
     {
       "id": "<app-id>",
       "label": "<App label>",
       "description": "<one sentence for the landing page card>",
       "repo": "RocketPadPlatforms/<repo>",
       "docsPath": "docs",
       "sidebarFile": "docs/sidebars.json",
       "source": "releases",
       "tagPattern": "^v?(\\d+\\.\\d+\\.\\d+)$",
       "minVersion": "<first release that has these docs>",
       "exclude": [],
       "retention": "all"
     }
     ```

   - the `TODO:` list.

## Release rules (put them in CONTRIBUTING or the README of the app)

- The portal publishes only **published** GitHub releases (no drafts, no prereleases) whose tag
  matches `vX.Y.Z`. Docs at a release are frozen: a docs fix for a released version needs a new
  patch release. Enable immutable releases in the repository settings.

## Caveats

- The `docs.yml` check calls a reusable workflow of the portal. While the portal's workflows run
  on a self-hosted runner, a **private** app repository must be allowed to use that runner group,
  otherwise the job waits in the queue forever. Ask a maintainer if the check never starts.
- This skill is loaded from the portal's `main` branch and cached for a few minutes by GitHub.
  After a skill update, wait briefly before relying on the new text.
